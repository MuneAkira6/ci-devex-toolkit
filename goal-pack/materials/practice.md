# 素材：著者の CI と開発体験の実践（このリポジトリを書くための一次資料）

> ワーカーへ：著者の実務について書いてよいことは、このファイルがすべてです。ここにないことを実務の話として書かないでください。書き方は自分の言葉で。実務の数字は一つも書きません（README の「結果」は事例へのリンクで示します）。会社・製品・チーム・人の名前は出てきませんし、書いてもいけません。サンプルの製品は架空の「Acme Tasks」です。

## 1. 状況

- バックエンドは Scala / Play（ビルドは sbt）、管理画面は React（パッケージ管理は pnpm）です。周辺に Gradle でビルドする小さな Java のプログラムがありました。
- 開発は Windows 上の devcontainer で行っていました。
- 社外への通信は、認証付きの社内プロキシを通ります。
- AI エージェントと仕事をするようになって、仕様、スキル、判断の台帳といった、製品のコードではない資産が急に増えました。

## 2. PR コンパイルチェック（self-hosted runner）

- コンパイルエラーに PR の段階で気づけず、デプロイのときに初めて分かることがありました。
- チームの Linux 開発機を self-hosted runner として登録し、PR ごとにバックエンドとフロントエンドをビルドするようにしました。
- `runs-on` を式にして、既定では self-hosted に流し、手動実行で選んだときだけ GitHub-hosted に振るようにしました。runner の機械が止まっているときの逃げ道です。
- JVM は認証付きのプロキシをそのまま使えません。そこで、runner 機の上に中継プロキシを置き、`127.0.0.1` だけにバインドしました。認証情報を持つのは中継プロキシだけです。
- ワークフローの権限は `contents: read` だけです。secret は一つも渡しません。
- 公開リポジトリから取れない依存は、リポジトリ内のローカルリポジトリに同梱し、secret なしで依存解決できるようにしました。self-hosted runner を安全に使う前提は、secret を渡さずに済む構成を作ることだと考えています。
- 同じ PR の古い実行はキャンセルし、ジョブにはタイムアウトを付けました。
- ワークスペースは毎回きれいにし、デプロイと同じ全量のビルドをします。チェックで実行するのは、パッケージングで実際に使われるタスク（sbt の `stage`）で、`compile` ではありません。
- 失敗した実行は「失敗したステップ」と「エラーのシグネチャ」で分け、コミットごとに並べました。同じコミットで成功と失敗が分かれていれば、非決定的な失敗です。そうやって見つけた原因の修正は、関心を一つに絞った別の PR に分けました。

## 3. devcontainer の I/O

- ローカルの起動が遅く、原因は、Windows のバインドマウント越しにビルド成果物と依存のキャッシュを読み書きする I/O でした。起動時の過剰なログも効いていました。
- ビルド成果物（sbt の `target/`）と依存のキャッシュを named volume に移し、ログのレベルを直し、取得できない依存をリポジトリ内に置きました。
- 効果は、開発者が自分の端末で測りました。実務の数字はこのリポジトリには書きません。

## 4. OSS ライセンス一覧

- 依存とライセンスの取り方が、npm / pnpm、sbt、Gradle でばらばらでした。毎回手で一覧を作っていました。
- ワークフローと生成スクリプトで、CSV・Markdown・第三者ライセンスの案内を出力するようにしました。
- フロントエンドは依存を自動で解析します。バックエンドと Gradle 側は、整備した対応表を使いました。
- ライセンスの全文が欠けている依存があれば、ジョブを失敗させます。黙って一覧から落とすことはしません。

## 5. 2 リポジトリ・1 作業ツリー

- AI 用の資産を製品リポジトリに混ぜたくない。ただし、既存のパスは変えたくない。これが条件でした。
- 資産用のリポジトリを bare で作り、製品リポジトリと同じ作業ツリーに重ねました。ファイルは一つも移動していません。
- 製品側は `.git/info/exclude` で資産を除外します。`.gitignore` に書くと、製品リポジトリの差分に出てしまうからです。
- 資産側は、ホワイトリスト式の exclude で自分の担当だけを拾います。
- ripgrep は `.git/info/exclude` も読むので、何もしないと検索結果から資産が静かに消えます。ルートの `.ignore` で、その除外を打ち消しました。
- 両方のリポジトリが同時に追跡しているパスが 0 件であることを、定期的に確かめています。
- 資産の置き場所は三つの条件で考えます。差分に出ないこと、検索から消えないこと、二つのリポジトリで重ならないこと。

- runner や開発機、プロキシ、ネットワークの具体的な構成（ホスト名、アドレス、アカウント、認証の方式、OS の版など）。「認証付きの社内プロキシ」「チームの Linux 開発機」より細かくは書きません。
- runner をどのユーザーで動かしていたかなど、実務の運用上の判断の細部。
- ビルドの失敗件数や、どんな欠陥が見つかったか。
- runbook には、テンプレートを使う人への一般的な助言（専用の OS ユーザーで動かす、フォークからの PR の扱い、など）を書いて構いません。ただし、それを著者の実務で行ったとも、行わなかったとも書かないでください。実務の話として書けるのは、上の 2〜5 にあることだけです。
