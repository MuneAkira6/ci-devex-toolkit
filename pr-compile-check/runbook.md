# PR コンパイルチェック — 運用手順書

このリポジトリの `pr-compile-check.yml` を自分のリポジトリに置いて、self-hosted runner で PR ごとの
ビルドを回すための手順書です。ルールの検査は `pnpm workflow:check`、中継プロキシは `relay/`、その試験は
`pnpm relay:test` が担当します。

> 書き方について：本文には二種類の文があります。**「実務では〜ました」** と書いてある文は、このリポジトリの
> もとになった実務で実際に行ったことです。**「〜するとよいでしょう」「〜をおすすめします」** と書いてある文は、
> このテンプレートを採用する方への一般的な助言で、実務で行ったとも行わなかったとも述べていません。

## 目的

PR の段階でコンパイルエラーに気づくことが目的です。実務では、コンパイルエラーに PR の段階で気づけず、
デプロイのときに初めて分かることがありました。そこで、チームの Linux 開発機を self-hosted runner として
登録し、PR ごとにバックエンドとフロントエンドをビルドするようにしました。

ここで走らせるのは、デプロイと同じ全量のビルドです。実務では、チェックで実行するタスクを、パッケージングで
実際に使われるもの（sbt の `stage`）にしました。`compile` は通っても `stage` で落ちるビルドは、デプロイできる
ビルドではないからです。ワークスペースは毎回きれいにします。

## 前提

- 対象は、sbt でビルドするバックエンドと、pnpm で管理するフロントエンドを持つリポジトリです。
- 社外への通信が認証付きのプロキシを通る環境を想定しています。JVM はこのプロキシをそのままでは使えません
  (後述)。
- runner を動かす機械が一台あること。GitHub-hosted runner だけで足りるなら、このテンプレートは要りません。
- `pr-compile-check.yml` の `push.branches` に書いてある `main` は、コピー先のリポジトリの既定ブランチです。
  違う名前なら書き換えてください。

## runner の登録

1. リポジトリの設定から self-hosted runner を追加し、表示される手順に従って runner を機械に登録します。
2. ラベルは `self-hosted`, `linux`, `x64` を前提にしています。違うラベルにする場合は、テンプレートの
   `runs-on` の式と、`pnpm workflow:check` が見る R4 の条件を合わせて読み替えてください。
3. runner は専用の OS ユーザーで動かすことをおすすめします。ビルドが書き込める範囲を、そのユーザーが
   触れる範囲に限れるためです。
4. 登録が済んだら、`workflow_dispatch` から一度手で流して、両方のジョブが緑になることを確かめるとよいでしょう。

runner に渡す secret はありません。実務では、ワークフローの権限は `contents: read` だけにし、secret は一つも
渡しませんでした。公開リポジトリから取れない依存は、リポジトリ内のローカルリポジトリに同梱して、secret なしで
依存解決できるようにしました。self-hosted runner を安全に使う前提は、secret を渡さずに済む構成を作ることだと
考えています。

## 中継プロキシ

JVM は認証付きのプロキシをそのまま使えません。sbt の依存解決は、プロキシが返す
`HTTP/1.1 407 Proxy Authentication Required` に自分で答えられず、そこで止まります
(測定の記録は `goal-pack/facts.md` の F12 です)。認証情報をビルドに渡せば動きますが、それは
「secret を渡さない」という前提を崩します。

そこで実務では、runner 機の上に中継プロキシを置き、`127.0.0.1` だけにバインドしました。認証情報を持つのは
中継プロキシだけで、ビルドは認証のいらないプロキシに向かって話します。

`relay/` の中身は次のとおりです。

| ファイル | 役割 |
|---|---|
| `compose.yml` | squid を一つ、`127.0.0.1:${RELAY_PORT:-3128}` にだけ公開します。イメージはダイジェスト固定です。 |
| `squid.conf.template` | 設定のひな形。`@UPSTREAM_HOST@` などの差し込み口を持ちます。 |
| `render-squid-conf.sh` | 起動時にコンテナの中でひな形を埋め、`/etc/squid/squid.conf` を 0600 で書きます。 |
| `.env.example` | `.env` のひな形。中身はすべてダミーです。 |

立ち上げかたは次のとおりです。

```
cd pr-compile-check/relay
cp .env.example .env          # .env は git 管理外です
$EDITOR .env                  # 上流プロキシのホスト・ポート・ユーザー・パスワードを書きます
docker compose up -d
```

設計上の約束がいくつかあります。

- **公開先は `127.0.0.1` だけです。** 外から届く中継プロキシは、他人の認証情報が入った open proxy です。
- **描画はコンテナの中で行い、結果をどこにも表示しません。** 認証情報の入った設定ファイルがホストに残らず、
  イメージの層にも入りません。`render-squid-conf.sh` は、値が空のときと値に空白が含まれるときに描画を
  拒んで終了します。squid の `login=user:password` には引用の構文がないため、空白の入った値は黙って別の
  意味になってしまうからです。
- **`never_direct allow all` です。** すべての通信は上流プロキシへ送られます。上流に届かないときは、別の経路に
  こっそり出るのではなく、失敗します。
- **キャッシュしません。** プロキシのキャッシュのせいで依存が古いまま通るビルドは、再現できません。

`pnpm relay:test` は、この `squid.conf.template` と `render-squid-conf.sh` をそのまま使って中継プロキシを
立ち上げ、認証付きの上流プロキシの代わりとなるモックと、宛先のモックを隣に置いて、仕様で決めた五つのことを
確かめます。五つめは対照実験で、上流の認証情報を間違えたときに要求が通らないことを確かめます。これが通って
しまうなら、残りの四つは何も証明していません。

実行時には、この五つに加えて二つを報告します。資格情報が `docker compose logs` に一度も現れないこと
（出現回数 0）と、どのコンテナにもプロキシの環境変数が渡っていないことです。したがって出力は `ok` が七行、
最後に `7 passed, 0 failed` となります。

## ワークフローのルール（R1–R9 と理由）

`pnpm workflow:check <file>` が一行ずつ検査します。`R1 ok` / `R1 FAIL <理由>` を印字し、すべて守られていれば
0、一つでも破れていれば 1、ファイルが読めないか YAML でなければ 3 で終了します。

| 規則 | 内容 | 理由 |
|---|---|---|
| R1 | `pull_request`、既定ブランチへの `push`、および runner を選ぶ入力を持つ `workflow_dispatch`（既定は self-hosted） | PR ごとに回すことが目的です。手動実行の入力は、runner の機械が止まっているときの逃げ道です。 |
| R2 | 最上位の `permissions` はちょうど `contents: read`。どのジョブも広げない | 実務では secret を一つも渡しませんでした。読み取りだけで足りる仕事に、それ以上の権限を与える理由がありません。 |
| R3 | `secrets.` がどこにも現れない。`pull_request_target` を使わない | `pull_request_target` は fork のコードを base リポジトリのトークン付きで走らせます。self-hosted runner と組み合わせると、他人のコードが自分の機械で特権付きに動きます。 |
| R4 | すべてのジョブの `runs-on` が式で、手動実行で hosted を選んだときだけ GitHub-hosted になる | 実務では `runs-on` を式にして、既定では self-hosted に流し、手動実行で選んだときだけ GitHub-hosted に振るようにしました。 |
| R5 | self-hosted で走りうるジョブは、head リポジトリが自分のリポジトリでない PR を拒む | fork からの PR は他人が書いたコードです。self-hosted runner は使い捨てではないので、一度動いたものが次の実行に残ります。 |
| R6 | `concurrency` を PR（または ref）ごとにまとめ、`cancel-in-progress: true` | 実務では、同じ PR の古い実行はキャンセルしました。すでに古いコミットの結果を待つ意味はなく、runner は一台です。 |
| R7 | すべてのジョブに `timeout-minutes` | 実務では、ジョブにタイムアウトを付けました。止まったビルドが runner を占有し続けないようにするためです。 |
| R8 | `actions/checkout` は必ず `persist-credentials: false` | 作業ディレクトリが残る機械では、`.git/config` に残った資格情報も残ります。 |
| R9 | すべての `uses:` が 40 桁のコミット SHA で固定され、版をコメントで添えてある | タグは動きます。動いたタグで走るのは、自分の機械の上の他人のコードです。コメントの版は、人が読むためのものです。 |

テンプレートを変えたら、`pnpm workflow:check pr-compile-check/pr-compile-check.yml` と `pnpm actionlint` を
通してください。前者は上の九つを、後者は GitHub Actions としての正しさを見ます。

## フォークからの PR

R5 により、fork からの PR では self-hosted で走りうるジョブが動きません。チェックは「実行されなかった」
状態になります。

- 取り込みたい PR については、内容を読んでから、自分のリポジトリにブランチとして取り込み、そちらで走らせる
  とよいでしょう。
- `pull_request_target` に切り替えて解決しようとしないでください。それは fork のコードに自分のトークンを
  渡すことになり、R3 が禁じている理由そのものです。
- どうしても fork の PR を自動で検査したいなら、GitHub-hosted runner だけで走る別のワークフローを用意し、
  secret を渡さない形にするのが穏当です。

## runner が止まったとき

1. 「Actions」から対象のワークフローを選び、`Run workflow` で手動実行します。入力 `runner` に
   `github-hosted` を選ぶと、両方のジョブが `ubuntu-24.04` に流れます。これが逃げ道です。
2. 機械が戻ったら、`runner` を既定の `self-hosted` のままで一度流し、緑になることを確かめます。
3. 中継プロキシが落ちている場合は、依存の取得だけが失敗します。`docker compose ps` と
   `docker compose logs relay` を見てください。ログに認証情報は出ません。
4. ディスクが埋まっていることもあります。作業ディレクトリと Docker の未使用領域を確認するとよいでしょう。

## 点検（定期的に見ること）

- **失敗の仕分け。** 実務では、失敗した実行を「失敗したステップ」と「エラーのシグネチャ」で分け、コミット
  ごとに並べました。同じコミットで成功と失敗が分かれていれば、それは非決定的な失敗です。そうやって見つけた
  原因の修正は、関心を一つに絞った別の PR に分けました。
- **固定の点検。** `pnpm workflow:check` と `pnpm actionlint` を CI で回し、`uses:` の固定が外れていないことを
  確かめます。
- **中継プロキシ。** `.env` が git 管理外のままであること、公開先が `127.0.0.1` だけであること
  （`docker compose port relay 3128`）を確かめます。`pnpm relay:test` は対照実験込みで一通りを見ます。
- **依存の同梱。** 公開リポジトリから取れない依存を同梱している場合、その一覧が実際の依存と合っているかを
  見ておくとよいでしょう。
- **runner の版。** runner と、`uses:` で固定しているアクションの版は、意図して上げるものです。上げたときは
  SHA とコメントの両方を書き換えてください。
